Client intake builder playbook

Use this checklist whenever you create or revise an intake form. Every control in the builder and JSON is documented below.

Before you start

  • Confirm the goal of the form (onboarding, follow-up, consent renewal, etc.) and who will fill it out (client, staff, both).
  • List the data points you must capture. Group them into logical sections (e.g. “General”, “Medical history”, “Preferences”).
  • Identify which answers are mandatory, which have suggested defaults, and which must follow strict formatting (dates, phone numbers, numeric ranges).
  • Decide whether this form replaces an existing schema. If so, plan the version bump and communicate downstream consumers of the data.

Toolbar reference

  • Add section: Inserts a blank section at the end of the form.
  • Load sample: Replaces the current layout with a comprehensive demo schema. Use it to explore features or as a starting point.
  • JSON editor: Opens the raw configuration for backup, bulk editing, or advanced tweaks. Changes are applied only after you click Apply.

Section workflow

  1. Title: Clearly state the topic so clients know what data is requested. Sections no longer support descriptions, keeping layouts concise.
  2. Reorder: Use Up/Down to relocate a section. The order here is the order presented to users.
  3. Delete: Removes the section and every field inside it. This action cannot be undone; export the JSON first if you might need to restore it.
  4. Add field: Appends a new question inside the section. Fields inherit the section order.

Field configuration checklist

  • Label: The human-friendly prompt shown to staff/clients. Write instructions (“List medications separated by commas”) when needed.
  • Type: Controls rendering and validation. Changing the type may reset incompatible settings (e.g. removing choices for non-choice fields).
  • Placeholder: Grey helper text shown in inputs before entry. Use sparingly to avoid confusing it with actual answers.
  • Advanced settings: Keys, required flags, defaults, helper copy, width, and custom validation live in the JSON editor. The builder auto-generates stable keys and keeps the UI focused on the essentials.

Field type reference

  • Text: Single-line input for short responses. Add regex or length rules via the JSON editor when needed.
  • Long text (textarea): Multi-line field for narratives or comments. Advanced validation also lives in JSON.
  • Number / Integer: Numeric input with optional Min / Max constraints. The JSON alias integer is also accepted.
  • Decimal / Float: Number input that accepts fractional values. Use Decimal places to force currency-like precision.
  • Boolean: Renders a checkbox; it stays unchecked unless you prefill it in JSON.
  • Select: Single choice dropdown. Define at least one option (value/label); defaults are configured via JSON.
  • Radio: Single choice rendered as radio buttons. Works like Select but always visible.
  • Multiselect: Multi-choice checkbox list. You may pre-select multiple defaults.
  • Date / Time / Date & time: Calendar and/or time pickers. Respect locale and timezone requirements downstream.
  • Email / Phone: Text inputs with additional validation applied on submission.

Choice management

  1. Each option needs both a Value (stored in JSON) and a Label (shown to users).
  2. For single-choice fields, selecting a default automatically clears previous defaults. For multiselect, toggle defaults independently.
  3. Use the × button to remove an option. The change is immediate in the builder.
  4. Add option inserts a blank choice at the end. Reorder options by dragging in the JSON editor if you need a precise order.

Validation & advanced settings

  • Numeric fields: Configure Min / Max to reject out-of-range values. Decimal fields also support Decimal places.
  • Text fields: Control Min length, Max length, and optional Pattern (regex) for custom validation (e.g. ^[0-9]{4}$ for a 4-digit PIN).
  • Duplication: Use Duplicate to clone a field; adjust the new key immediately to avoid duplicates.
  • Ordering: Up/Down buttons update the order instantly. Verify the final order before saving to guarantee a logical flow.

Meta and versioning

  • Schema version: Update meta.version via the JSON editor whenever you introduce a breaking change (key rename, removed question, or semantic shift).
  • Non-breaking updates (copy edits, help text tweaks) can stay on the same version, but bumping the number still improves traceability.
  • Store release notes elsewhere if teams need historical context—only the version value lives inside the schema.

Saving, testing, and publishing

  1. Click Save or Save and continue editing in the right column to persist changes.
  2. After saving, reopen the form to confirm the layout matches expectations. Review on both desktop and mobile breakpoints.
  3. Submit a test appointment or intake entry to ensure downstream processing (webhooks, exports, analytics) understands the new keys.
  4. If a custom Django Form class is configured, keep it in sync with the JSON schema or switch back to the builder-driven intake.

Troubleshooting

  • Duplicate keys: Ensure every field key is unique. The admin form will block the save if duplicates remain.
  • Invalid JSON error: The JSON editor validates syntax when you click Apply. Fix commas/braces and try again.
  • Unexpected defaults: Confirm that default values match the field type (e.g. strings for text, booleans for checkboxes).
  • Lost work: Use the JSON editor to copy the schema regularly, or version the exported JSON in source control.

Authoring JSON manually (exhaustive guide)

  1. Top-level structure: Always provide an object with two keys: meta (object) and sections (array).
  2. Meta object: At minimum include version (positive integer). You can add extra metadata (e.g. title, description) for downstream systems—unknown keys are preserved.
  3. Sections array: Each entry is an object. Recommended properties:
    • id: Stable identifier (UUID or slug). Optional but helps with diffing.
    • title: Required. Displayed heading.
    • description: Optional explanatory text (JSON editor only).
    • fields: Array of field objects (see below).
  4. Field object essentials:
    • id: Unique identifier (UUID). Auto-generated if omitted.
    • key: Required slug (letters/numbers/underscores, starting with a letter). Drives storage.
    • label: Required human prompt.
    • type: One of text, textarea, number, decimal, boolean, select, radio, multiselect, date, time, datetime, email, phone.
    • required: Boolean (defaults to false).
  5. Optional field attributes:
    • placeholder (builder) plus help_text / default (JSON editor only)
    • display: Object with width (full or half)—edit in JSON if you need multi-column layouts.
    • settings: Object for validation extras (JSON editor):
      • min_value / max_value (numbers)
      • decimal_places (decimals)
      • min_length / max_length (text)
      • pattern (regex string for text)
    • choices: Array for choice-based fields. Each choice has value, label, and optional default boolean (set via JSON).
  6. Validation rules: Respect JSON data types—numbers without quotes, booleans as true/false, and strings wrapped in quotes. Keep arrays ordered as you want options displayed.
  7. Applying changes: Paste the JSON into the editor, click Apply, verify the preview, and then Save the Django form. Use Reset to roll back to the last applied state.
  8. Version control: Store exported JSON alongside your codebase for auditing. Commit schema version bumps with release notes to avoid accidental regressions.
